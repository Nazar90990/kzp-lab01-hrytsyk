# Звіт до лабораторної роботи №2

## Тема і варіант

- Предметна область: комунальні показники.
- Варіант: `meter:String; date:String; value:double; tariff:double`.
- Система розробки: Windows, Java 25, Maven.
- Гілка лабораторної роботи: `lab-02-java`.

## Мета та перенесення з лабораторної роботи №1

Мета роботи — замінити плоске представлення перевіреного запису на повноцінний незмінний клас-сутність, не змінюючи формули показників, формат звіту та поведінку обробки помилкових рядків.

З лабораторної роботи №1 перенесено:

- формат рядка `meter;date;value;tariff`;
- правила перевірки назви лічильника, дати, споживання та тарифу;
- пропуск некоректного рядка з номером і причиною помилки;
- обчислення сумарного споживання, загальної вартості та найбільшого споживання;
- форматування звіту з двома знаками після крапки.

Перед рефакторингом контрольний запуск мав 3 коректні записи, сумарне споживання `202.80`, загальну вартість `1361.91 грн`, найбільше споживання `145.50` і 2 помилки. Після рефакторингу ці значення збережено.

## Клас-сутність

`UtilityRecord` — `final`-клас із чотирма `private final`-полями: `meter`, `date`, `value` і `tariff`. Сеттери відсутні, тому після створення об'єкт не можна змінити.

Конструктор відхиляє:

- `null` і порожню назву лічильника;
- `null` і порожню дату;
- дату, яка не відповідає формату `YYYY-MM-DD`;
- від'ємні, нескінченні та `NaN` значення `value` і `tariff`.

Клас має accessor-методи `meter()`, `date()`, `value()`, `tariff()` і геттери `getMeter()`, `getDate()`, `getValue()`, `getTariff()`. Метод `toString` форматує числа через `Locale.ROOT`.

## Фабрика fromCsv і розбір даних

Статичний метод `UtilityRecord.fromCsv` перевіряє непорожній рядок, кількість із чотирьох полів і перетворює числові значення. Після цього конструктор класу повторно забезпечує інваріанти об'єкта.

`UtilityRecordParser` залишено як сумісний фасад, який делегує розбір методу `UtilityRecord.fromCsv`. Основний цикл `Main` додає об'єкт до списку лише після успішного створення. Номер рядка додається до повідомлення на рівні циклу читання, тому некоректний запис не впливає на статистику.

## Допоміжний record

`UtilityReportCalculator.Summary` — незмінний record для передачі підсумків: кількості коректних записів, сумарного споживання, загальної вартості та найбільшого споживання. Формули та формат звіту залишилися без змін.

## Тестування

До чотирьох регресійних тестів лабораторної роботи №1 додано:

- перевірку конструктора на `null`, порожній текст, від'ємні, `NaN` та нескінченні значення;
- перевірку `fromCsv` для неправильного числа полів, числа, дати та порушення інваріанта;
- перевірку accessor-методів, `equals`, `hashCode` і `toString`;
- перевірку рівності та доступу до компонентів record `Summary`.

Виконані команди:

```text
mvnw.cmd test
mvnw.cmd clean verify package
java -jar target/lab01-2.0.0.jar --input data/input.csv --output out/report.txt
```

Очікуваний результат запуску: 3 коректні записи, сумарне споживання `202.80`, загальна вартість `1361.91 грн`, найбільше споживання `145.50`, 2 помилки. Maven Verify проходить разом зі SpotBugs, а Maven Shade Plugin створює виконуваний JAR.

## GitHub Issues і Pull Request

Для роботи створено Issues для класу-сутності, фабрики та валідації, тестів і документації. Розробка виконується у гілці `lab-02-java`, після перевірки зміни мають бути об'єднані в `main`. Фінальний стан лабораторної фіксується у гілці `lab-02-java`.

Pull Request повинен містити посилання `Closes #N`, результати локальної перевірки та зелений CI на Ubuntu, Windows і macOS.

## Інфраструктура та CI

GitHub Actions у `.github/workflows/ci.yml` запускає `clean verify package` на `ubuntu-latest`, `windows-latest` і `macos-latest`, перевіряє `--version` та публікує `target/lab01-2.0.0.jar` як артефакт. Workflow запускається для `main`, `lab-01-java` і `lab-02-java`.

## Версія

Версію програми оновлено з `1.0.0` до `2.0.0`. Нова версія записана у `pom.xml`, виводиться через `--version` і фіксується Git-тегом `v2.0.0`.
